# ADR-0019: 参加者に対する操作の可否はサーバーが返す（画面は立場から組み立て直さない）

- 日付: 2026-08-02
- 状態: 承認
- 関連: ADR-0009（家族の認可表）、ADR-0010（追記専用台帳）、ADR-0011（子の
  一時パスワード）、ADR-0013（所属は 1 家族まで）、ADR-0014（子の独立）
- 対象: `bounded_contexts/reward_points/`、`frontend/src/`

## 文脈

家族の詳細画面は、参加者ごとの操作（一時パスワード・独立の指示・除名）を
**画面側が立場から組み立てて**出していた。サーバーの断り方はもっと細かい。

- 除名は台帳が空のときだけ通る（記録が残っていれば `ledger_not_empty` — ADR-0010）。
- 独立の指示はアカウントの結び付いた子にだけ通る（`membership_not_linked`）。
- 一時パスワードも本人のアカウントが要る。

その結果、押した瞬間にエラーだけが返る操作が並んでいた。押せるように見えるのに
断られるので、利用者からは不具合と区別が付かない。

同じねじれが家族の入口にもあった。所属できる家族は 1 つまで（ADR-0013）なのに、
すでに所属している人へ「家族を作る」「コードで参加する」を出し続けており、
どちらも `already_belongs_to_family` に落ちる。

## 決定

1. 参加者ごとの操作の可否は、家族の詳細応答が
   `can_reset_password` / `can_graduate` / `can_remove` として返す。画面はこの
   3 つだけを見て操作を出す。判定はドメインの `family_access_policy` にあり、
   ユースケースが断る条件と同じ関数を使う。
2. 子を家族から外す道は 2 つで、画面でも別々の操作として出す。
   **卒業**（ADR-0014 の独立）と **削除**（記録の無い参加者のみ）。
3. すでに家族へ所属している人には、作成・参加の入口を出さない。所属していれば
   家族の詳細（家族設定）へ送る。

## 理由

台帳の `can_modify`（ADR-0007）がすでに同じ形で、画面の出し分けをサーバーの
答えに委ねている。可否の根拠は「立場」だけでなく「台帳に記録があるか」
「アカウントが結び付いているか」といったサーバー側の状態を含むので、画面が
組み立て直せば必ずずれる。ずれた分がそのまま「押すと失敗するボタン」になる。

「卒業」と「削除」を 1 つの操作（除名）に見せていたのも、同じずれの現れだった。
成長した子を外す道（卒業）と、間違えて作った参加者を消す道（削除）は、
起きることも承認の要否も違う。画面で 1 つに見せると、どちらの説明も嘘になる。
画面上の呼び名を「卒業」にしたのは家庭内の語彙に寄せたもので、API・DB・ADR の
語彙は「独立（independence）」のまま変えていない。

### 代替案: 押した後のエラー文言を分かりやすくする

失敗を丁寧に説明しても、できないことが並んでいる事実は変わらない。操作の一覧が
「今できること」を表さないままになる。

### 代替案: 可否を画面側の関数に集約する

1 か所にはなるが、サーバーの状態（記録の有無）を画面が持っていないので、
結局は同じずれが残る。判定の重複も生む。

## 影響

- 参加者 1 人を作って返すだけの応答（子の追加・独立の指示）は、家族全体を
  読み直さないので可否を答えられない。これらの `can_*` は常に偽で返し、画面は
  操作の直後に家族を読み直す。可否を見るのは家族の詳細応答だけとする。
- 判定を足すときは `family_access_policy` に関数を足し、ユースケースと
  `FamilyOverviewBuilder` の両方から同じものを呼ぶ。片方だけに書くと、また
  ずれが生まれる。
- 所属は 1 家族までという前提が画面の構造にも入った（家族の一覧を持たない）。
  複数所属へ戻す場合は ADR-0013 と併せて見直す。
