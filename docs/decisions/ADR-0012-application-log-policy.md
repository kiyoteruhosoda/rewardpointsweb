# ADR-0012: アプリログは「失敗と管理操作」を中心に残す — 記録の場所とレベルを 1 か所で決める

- 日付: 2026-08-01
- 状態: 承認

## 文脈

`log` テーブルはこのアプリで唯一の記録である（監査ログのような別テーブルは持って
いない）。しかし運用で必要になる情報が残っていなかった。

- **失敗が記録されない。** `HTTPException`・入力検証エラー・ドメイン例外は、送出
  された時点でルーターを抜け、例外ハンドラが応答へ変える。ルーターに `logger` を
  足しても通らない経路で、残るのはアクセスログの 1 行（ステータスコードだけ）。
  「どのエラーコードで落ちたか」「どの項目が検証に落ちたか」がどこにも無い。
  想定外の例外（500）だけは traceback 付きで残っていた。
- **管理操作が記録されない。** アカウントの追加・変更・削除、ロールの権限変更、
  システム設定の保存は、成功しても何も残らない。他人のアカウントと権限を変える
  操作で、「いつ誰のアカウントが変わったか」を後から追えない。
- **失敗したログインが記録されない。** 401 で終わり、試行が続いているかが見えない。
- **レベルで絞り込めない。** アクセスログは成功も失敗も一律 INFO。WARNING 以上で
  絞っても異常が浮かび上がらない。
- **死活監視でログが埋まる。** Docker の healthcheck が数十秒おきに `/healthz` を
  叩き、その 200 の行が `log` の大半を占める。1 件ずつは「異常が無かった」以上の
  情報を持たないのに、本当に見たい行を押し流す。
- **ログ基盤自身の失敗が見えない。** `DbLogHandler` と設定の DB 読み取りは例外を
  `pass` で捨てていた。症状は「管理画面にログが出ない」「保存した設定が効かない」
  だけになり、原因（DB 未接続・マイグレーション前）がどこにも残らない。

## 決定

1. **失敗の記録を `presentation/fastapi/error_handling.py` に集約する。**
   `HTTPException`・`RequestValidationError`・`Exception` のハンドラをここで登録し、
   ドメイン例外のハンドラ（各コンテキストの `error_handling`）は記録だけを
   `log_failed_request()` に委ねる。ルーターに `try/except` を書き足さない。
2. **ログのレベルはステータスコードから決める**（`log_level_for_status()`）。
   5xx → ERROR、4xx → WARNING、401 と成功 → INFO。アクセスログと失敗の記録が
   同じ関数を使う。**失敗したログインだけは例外的に WARNING** で残す。
3. **管理操作（ユーザー・ロール・システム設定の変更）をルーターから記録する。**
   識別子は `extra` ではなく**本文（message）に入れる**。
4. **死活監視・メトリクスのパス（`/healthz` `/readyz` `/api/health` `/metrics`）は
   アクセスログに残さない。ただし 4xx・5xx は残す。**
5. **ログ基盤の失敗は黙らない。** `DbLogHandler` は `handleError()`（stderr）で
   知らせ、設定の DB 読み取り不能は状態が変わったときだけ 1 行警告する。

## 理由

- **失敗はルーターの外側で起きる**という事情がそのまま設計になる。記録をハンドラへ
  置けば漏れが構造的に無くなり、レベルと項目（`error_code` / `invalid_fields` /
  `status_code`）も揃う。ルーターごとに書くと、書き忘れた経路だけが静かに消える。
- **識別子を本文に入れる**のは、`log` テーブルへ入るのが列にある項目
  （`message` / `path` / `method` / `status_code` / `duration_ms` / `trace`）だけで、
  `extra` の残りは stdout の JSON にしか出ないため。管理画面（`/admin/logs`）から
  読めない記録は、残していないのとほぼ変わらない。列を足す案も考えたが、記録したい
  項目は操作ごとに違う（`user_id` / `role_id` / 設定キー）ので列にならない。
- **記録するのは識別子と項目名だけ。** 表示名・メールアドレス・設定値そのものは
  残さない（CLAUDE.md「ログ」）。人の特定は `user_id` から辿る。
- **ログインの失敗を WARNING に上げる**のは、このアプリに監査ログが無く `log` が
  唯一の手がかりだから。401 全体を WARNING にすると期限切れトークンの再取得で
  WARNING が埋まるので、ログイン経路だけを明示的に上げる。
- **プローブを残さない**のは、成功したプローブが情報を持たないため。「量が問題なら
  ログレベルを上げればよい」も検討したが、それでは他の INFO（`login_succeeded`・
  管理操作）まで一緒に消える。**失敗したプローブは残す**——プローブが落ちていること
  自体が知りたい情報で、ここで捨てると監視の対象が監視できなくなる。
- 記録するパスを設定キーにする案は採らなかった。除外したいのはアプリが自分で
  公開している運用エンドポイントで、環境ごとに変わるものではない。設定にすると
  「なぜこのパスが消えているのか」を設定値まで追う必要が出る。
- **入力検証の記録には項目名と理由だけを入れる**（`body.password:missing`）。`ctx` や
  `input` を入れると入力値がログへ移る。

## 影響

- アクセスログの行数が減る。`/healthz` の 200 を見て死活を確認する運用はできない
  （`docker compose ps` の healthcheck 状態か Prometheus の `/metrics` を見る）。
- WARNING の件数が増える。404・409・422 が WARNING として残るため、「WARNING が
  出ている＝障害」ではなくなる。障害の判定は ERROR で行う。
- 新しいドメイン例外ハンドラを足すときは `log_failed_request()` を呼ぶ。呼ばないと
  その例外だけ記録が抜ける。
- 管理操作を足したときは、同じ形（`<操作>: <識別子>`）でルーターから記録する。
- 「誰が」を主体として記録する仕組み（監査ログ）はまだ無い。実行者は
  `user.id_hash` と `requestId` から辿る。必要になった時点で別の ADR で決める。
