# ADR-0029: SSO は既にある利用者への入口に限る

- 日付: 2026-09-02
- 状態: 承認

## 文脈

自前の IdP（`idp.nolumia.com`）で他のアプリと同じアカウントを使いたい、という
要望が出た。OpenID Connect のクライアントとして繋ぐこと自体は定型だが、
**IdP が名乗った相手をこのアプリの誰として扱うか**は自明ではない。

このアプリの利用者には 2 種類ある（ADR-0011）。

- 親（メンバー）— メールアドレスを持ち、自分で登録・招待を受ける
- 子ども — **メールアドレスを持たない**。親が作り、親が一時パスワードを配る

一般的な SSO の実装は「知らない相手が来たら作る」（auto-provisioning）が既定に
なっている。しかしこのアプリでアカウントを作るということは、**家族のどこにも
属さない利用者が増える**ということで、作った人（親）も本人も何もできない。
子どもはメールアドレスを持たないため、IdP の名乗りから作れる利用者はそもそも
親だけに限られる。

もう 1 つ、`redirect_to` の扱いに固有の制約がある。招待コードは URL の断片で運ぶ
決まりで、クエリへ移した時点でアクセスログとリクエストログに平文で残る
（ADR-0025）。SSO は IdP の画面を挟むので断片が失われる。

## 決定

1. **SSO で利用者を作らない。** IdP の名乗りは、**検証済みのメールアドレス**が
   一致する既存の利用者へ結び付けるだけとする。一致しなければログインを断る
   （`sso_account_not_linked`）。
2. 一度結び付いたら `(issuer, subject)` を控え、以後はそれで決める。メールアドレス
   は変わり得るので、鍵にはしない。
3. 従来のログイン（パスワード・パスキー）は残す。子どもはメールアドレスを
   持たないため、SSO だけにすると入れない。
4. IdP からの戻りでは**トークンを URL に載せない**。1 回限りの引き換え券を渡し、
   SPA が `POST /api/auth/sso/token` でトークンへ換える。
5. 招待コードは `redirect_to` に載せない。IdP への往復のあいだは同じタブの
   `sessionStorage` に預け、戻ってきた画面で付け直す。

## 理由

- **アカウントの入口を増やさない。** 誰がこのアプリを使えるかは、いまも管理画面と
  招待の 2 つだけで決まっている。SSO を 3 つ目の入口にすると、IdP 側で誰かを
  作った瞬間にこちらにも利用者が生えることになり、家族の外に宙に浮く。
- **結び付けは検証済みのアドレスに限る。** IdP が検証していないアドレスで寄せると、
  他人のアドレスを名乗るだけでそのアカウントへ入れてしまう。
- **メールアドレスは識別子ではない。** このアプリの識別子は `username` で、
  メールアドレスは任意項目（ADR-0011）。初回に相手を見つける手掛かりとしてだけ
  使い、以後は `(issuer, subject)` で決める。
- **トークンを URL に載せない。** 戻りはブラウザの画面遷移なので、載せると履歴・
  `Referer`・アクセスログに残る。券なら漏れても 1 回・数十秒で失効する（DB には
  ハッシュだけを置く）。
- **`state` だけでは足りない。** 控えの表は全員で共有するので、`state` を知っている
  相手なら誰でも戻りを完了できる。攻撃者が始めた認可要求を被害者に踏ませると、
  被害者は攻撃者としてログインした状態になる（ログイン CSRF）。送り出すときに
  Cookie へ置いた合言葉と突き合わせる。
- 捨てた案: **auto-provisioning を設定で切り替えられるようにする。** 使わない枝と
  設定項目（作成時のロール・グループの対応付け）が丸ごと残る。既定を false に
  しても、いつか true にされたときの振る舞いを誰も確かめていない状態になる。
- 捨てた案: **`username` で突き合わせる。** IdP 側の名乗りとこちらの識別子が同じ
  である保証がなく、検証済みかどうかの概念も無い。
- 捨てた案: **管理画面で 1 人ずつ `subject` を貼る。** 安全だが、親が数人しか
  いない規模に対して画面と手順が重すぎる。

## 影響

- **メールアドレスを持たない利用者は SSO で入れない。** 子どもは従来どおり
  パスワード（またはパスキー）で入る。親も、アカウントにメールアドレスが
  入っていなければ先に設定する必要がある。
- IdP 側でメールアドレスを変えても、**一度結び付いた後なら**入れる。逆に、
  初回の結び付けの前に変えられると別人として扱われ、断られる。
- 一時パスワードの状態（`must_change_password`）は SSO で入っても解けない。
  親が発行した一時パスワードの意味を保つため（ADR-0011）。
- `private_key_jwt` を使う場合、秘密鍵はホスト上のファイルにある。**読めるか
  どうかは署名のときになって初めて分かる**ため、起動時にも一度確かめてログへ
  出す（`presentation/startup_check.py`）。
- 追加した表は 3 つ（`federated_identities` / `sso_login_sessions` /
  `sso_login_tickets`）。控えと券をプロセスのメモリではなく DB に置くのは、
  Gunicorn の複数ワーカーで送り出しと戻りのプロセスが一致しないため。
