# ADR-0015: 残高・履歴はオフラインでも閲覧できるようにする（network-first）

- 日付: 2026-08-01
- 状態: 承認

## 文脈

Service Worker は SPA のシェルだけを precache しており、API 応答はキャッシュして
いなかった。インストールしてホーム画面から開けるのに、圏外では残高も履歴も
表示できない。

キャッシュをためらっていた理由は「古い残高を見せ得る」こと。加算・消費は複数の
親が同じ台帳へ記録するため、古い残高を根拠に消費を記録されると実際の残高と
食い違う。一方で台帳を追記型にしたこと（ADR-0010）で書き込み側の懸念は整理
済みで、残るのは「閲覧をどこまで許すか」だった。

## 決定

閲覧系の GET だけを Service Worker の **network-first** でキャッシュし、
オフライン時のフォールバックとして使う。対象は次の 4 つ。

- `/api/auth/me`（オフラインでの起動にログイン状態の復元が要る）
- `/api/families`（一覧）
- `/api/families/{id}`（家族の詳細）
- `/api/families/{id}/ledgers/{id}`（残高・履歴）

台帳画面には応答の `Date` ヘッダーから**最後に取得した時刻**を常に表示する。
書き込み（加算・消費・打ち消し）はキャッシュせず、オフラインではこれまで通り
失敗する（オフラインキューは作らない）。キャッシュはトークンを消すとき
（ログアウト・セッション失効）に一緒に削除する。

## 理由

- **stale-while-revalidate ではなく network-first を選んだ**。SWR は
  オンラインでもまずキャッシュを返すため、記録直後の再取得が古い残高を
  一瞬表示する（同じ画面で記録→再読込するのが基本動線なので、これは常に
  起きる）。network-first ならオンラインの表示は常に最新で、古い値が出るのは
  オフラインのときだけに限定できる。
- **古い値であることを時刻で示す**。オフラインで出す応答は Service Worker が
  保存時のヘッダーごと返すため、`Date` ヘッダーがそのまま「いつの情報か」に
  なる。画面は常にこの時刻を出し、判断は見る人に委ねる。
- **書き込みは対象外**。台帳は追記型で `idempotency_key` により再送も安全
  だが、オフラインキューは「送信待ちの見せ方」「失敗時の破棄」の UI を伴う。
  閲覧の要望（T2）とは別の仕事なので切り離す。
- **`/api/auth/me` を含める**。起動時にログイン状態を復元できないと、他を
  キャッシュしてもログイン画面へ落ちてオフライン閲覧が成立しない。
- **キャッシュはトークンと同時に消す**。応答には個人のポイント記録が入る。
  ログアウト後に同じブラウザで別のユーザーがログインしても、前のユーザーの
  キャッシュが出ないようにする。削除は `clearTokens()`（`api.ts`）に置き、
  トークンを消すすべての経路（ログアウト・リフレッシュ失敗）で一緒に消える。

検討して捨てた代替案:

- **オフラインでは何も見せない（現状維持）**: 残高を確認するだけの用途
  （外出先・電波の悪い場所）が PWA にした動機の一つで、閲覧すら
  できないのは目的に合わない。
- **stale-while-revalidate**: 上記の通り、オンラインでも古い値が見える。
- **フロントエンドが localStorage へ自前で保存する**: Service Worker と二重の
  キャッシュ機構になり、消し忘れの経路が増える。HTTP キャッシュの単位
  （URL・ヘッダー）で扱うほうが素直。

## 影響

- 招待・理由の候補・管理系 API はキャッシュしない。オフラインではこれまで通り
  エラーになる（候補が取れなくても記録フォームは出る、等の既存の縮退のまま）。
- オフラインで表示する残高は古い可能性がある。画面の取得時刻がそれを示す。
- キャッシュ名（`offline-views`）は `frontend/vite.config.ts` と
  `frontend/src/services/api.ts` の双方が参照する。変えるときは両方を変える。
- 台帳の API 応答形が変わったわけではない。フロントの `families.viewLedger` の
  返り値だけが `{ data, fetchedAt }` になった。
