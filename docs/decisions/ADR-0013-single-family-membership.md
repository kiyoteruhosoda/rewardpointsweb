# ADR-0013: 家族への所属は 1 アカウント 1 つまでとし、脱退・解散・改名を定める

- ステータス: 承認
- 日付: 2026-08-01
- 関連: ADR-0009（家族グループを共有単位とする）の「複数所属の許容」を置き換える。
  役割・台帳・招待の構造は ADR-0009 のまま。
- 対象: `bounded_contexts/reward_points/`

## コンテキスト

ADR-0009 は「1 つのアカウントが複数の Family に所属することを許容する（別居親・
再婚等）」としていた。しかし家族の運用ルールを定めるにあたり、所属を単一とする
方が一貫した簡潔なモデルになると判断した。目指すルールは次のとおり。

1. どの家族にも所属していないアカウントだけが、家族を作れる（作った人が owner）。
2. 家族は、参加者が残っているうちは解散できない。
3. 親（メンバー）は、他に親が残るなら家族から抜けられる。抜けたら初期状態と同じで、
   元の家族とは縁が切れる。
4. 子（ゲスト）は家族に追加できるが、自分では家族から抜けられない。
5. 家族名は変えられる。
6. 所属の経路は「招待を受ける」か「自分で作る」の 2 つだけ。

従来の実装には脱退・解散・改名の操作が無く、複数所属を許すテストも存在した。

## 決定

### 所属は 1 アカウント 1 家族まで

役割（owner / parent / child）を問わず、アカウントは同時に 1 つの家族にしか
所属できない。次の 2 箇所で検査する（`already_belongs_to_family`）。

- 家族の作成（`CreateFamilyUseCase`）
- 招待の受諾（`InvitationBinder` — `accept` / `redeem` の両経路が通る）

DB 制約（`UNIQUE (account_id)`）は加えない。`account_id` が NULL の未紐付け参加者を
多数並べる必要があり、既存の `UNIQUE (family_id, account_id)` と併存させる価値が
検査 2 箇所のアプリケーション実装に対して薄いため。競合ウィンドウは残るが、
家庭内アプリの同時実行では実害がないと判断した。

### 脱退（leave）— `POST /api/families/{family_id}/leave`

- 抜けられるのは親（owner / parent）だけ。子は抜けられない
  （`child_cannot_leave_family`）。
- 他に親が残る場合だけ抜けられる（`last_guardian_cannot_leave`）。親が誰も
  いなくなると、残された子の台帳を扱える人がいなくなるため。1 人だけなら
  脱退ではなく解散を使う。
- owner が抜けるときは、最も古くから居る parent（`created_at`、同時なら ID）が
  owner を引き継ぐ。家族が管理者を失う瞬間を作らない。
- 参加は削除し、台帳の記録は家族に残す。操作者への参照は外れる
  （`granted_by_membership_id` は `ON DELETE SET NULL`）。抜けた後は初期状態と
  同じで、家族を作り直すことも招待を受け直すこともできる。

### 解散（dissolve）— `DELETE /api/families/{family_id}`

- owner だけができる。
- 自分以外の参加者（親も子も）が残っているうちはできない（`family_not_empty`）。
  台帳ごと黙って消える経路を作らない（ADR-0010）。子の参加は台帳が空であれば
  除名で先に外せる。記録が残る子がいる家族は解散できない — 履歴の保存を優先する。
- 未使用の招待は家族と一緒に消える（外部キーの CASCADE）。

### 改名（rename）— `PATCH /api/families/{family_id}`

owner だけができる（`can_administer_family` の記述どおり）。

### ゲスト（子）がメンバーになりたいとき

子は自分では抜けられないため、経路は「owner が除名（台帳が空の場合のみ）→
初期状態に戻ったアカウントが家族を作るか招待を受ける」となる。記録が残る子の
独立（アカウントの切り離しと台帳の凍結）は本 ADR の範囲外とし、必要になった
時点で別の ADR として設計する。

## 結果

### 良い点

- 「所属していなければ作れる」「抜けたら初期状態」という対称なルールになり、
  画面・説明・テストが簡潔になる。
- 家族がデータ分離の境界であることが強くなる（1 アカウントの視界は常に高々 1 家族）。

### トレードオフ

- 別居親・再婚など、1 人が複数の家族に関わる形は表現できなくなった。必要に
  なった場合はこの ADR を置き換える。
- 記録の残る子がいる家族は解散できず、実質的に永続する。履歴を黙って消さない
  ことを優先した意図的な制約。

## 検討した代替案

### 役割を変えるだけの昇格（child → parent）

同じ家族の中で子を親に昇格させる案。昇格した瞬間に兄弟全員の台帳が見えてしまい
（ADR-0009 の認可表）、「家を出たい」という動機に対して過剰な権限になる。また
本人の台帳に記録が残る限り除名できない問題が親になっても残る。採用しない。

### owner の脱退を禁じ、引き継ぎ専用操作を設ける

明示的な引き継ぎは意図が明確になるが、「他のメンバーがいれば抜けられる」を
owner だけ満たせなくなる。脱退時の自動引き継ぎ（最古参の parent）は決定的で
説明も短いため、専用操作は必要になってから足す。
