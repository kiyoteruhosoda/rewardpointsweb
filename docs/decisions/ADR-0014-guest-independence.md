# ADR-0014: ゲスト（子）の独立 — 親の指示と本人の承認で家族から離れる

- ステータス: 承認（アプリケーションロールの名前は ADR-0018 が再編。本文の
  「member から manager へ」は現在は「guest から member へ」に当たる）
- 日付: 2026-08-01
- 関連: ADR-0013（所属は 1 家族まで）の「範囲外」とした部分を設計する。
  ADR-0010（追記専用台帳）に明示的な例外を 1 つ設ける。
- 対象: `bounded_contexts/reward_points/`

## コンテキスト

子（ゲスト）は自分では家族から抜けられない（ADR-0013）。owner による除名は
台帳が空の場合に限られるため、記録の残る子が成長して「所属なしのメンバー」に
なる経路が存在しなかった。

## 決定

独立は **親メンバー（owner / parent）の指示** と **子本人の承認** の 2 段階で
成立する。どちらか一方の意思では成立しない。

### 指示 — `POST /api/families/{id}/memberships/{mid}/independence-proposal`

- 親メンバー（owner / parent）が、アカウントの結び付いた子に対して指示する。
  未紐付けの子は承認のしようがない（本人がログインできない）ので対象外 —
  そちらは従来どおり除名を使う。
- 指示は `family_memberships.independence_proposed_at` に記録され、家族の
  詳細応答に `independence_proposed` として現れる（子本人にも見える）。
- 承認されるまでは `DELETE`（同パス）でいつでも取り下げられる。

### 承認 — `POST /api/families/{id}/independence`

指示を受けた子本人だけが呼べる。成立すると:

1. **参加・台帳・全ての記録を家族から削除する。** 追記専用（ADR-0010）の
   唯一の例外。削除は独立の儀式に限られ、行単位の削除は今後も設けない
   （リポジトリの口も `delete_by_ledger` のみ）。
2. アカウントは残り、どの家族にも所属しない**初期状態**になる。
3. アプリケーションロールを子の閲覧専用（`member`）から親と同じ
   （`manager`）へ昇格する。昇格しないと「所属なしのメンバー」が家族を
   作ることも（`family:manage`）、ポイントを記録することも（`point:manage`）
   できず、独立が名ばかりになる。

独立後は ADR-0013 のルールがそのまま適用される: 家族を作れば owner になり、
招待を受ければメンバー（parent）として所属する。元の家族に戻る場合も新しい
参加として扱う（履歴は引き継がない）。

scope は JWT に焼き込まれているため、昇格した権限は**再ログイン後**に有効に
なる。画面は独立の成立後に再ログインを促す。

## 結果

### 良い点

- 「ゲストは自分では抜けられない」を保ったまま、双方の合意による退出経路ができた。
- 独立後のアカウントが完全な初期状態（所属なし・メンバー相当の権限）になり、
  ADR-0013 の対称なルールにそのまま乗る。

### トレードオフ

- 独立した子のポイント履歴は消える。家族に残す選択肢（凍結アーカイブ）も
  検討したが、「家族から削除し所属なしのメンバーとなる」という要件に合わせ、
  削除を選んだ。消えることは 2 段階の合意の前提として画面で示す。
- ロール昇格により、独立した元・子アカウントは item 管理やログ閲覧など
  `manager` ロールの持つ他の scope も得る。専用ロールを設けるほどの違いが
  出た時点で分離する。

## 検討した代替案

### 台帳を凍結して家族に残す（アカウントの切り離しのみ）

履歴が消えない一方、「家族から削除」にならず、名簿に居続けるか、隠すための
状態管理が増える。要件と合わないため採用しない。

### 子本人の宣言だけで成立させる

「ゲストは家族から抜けられない」を実質無効にしてしまう。親の指示を起点に
することで、家族の構成変更が親の管理下にあるという原則を保つ。

### owner の指示だけで成立させる（本人の承認なし）

本人の与り知らないところでアカウントの権限と所属が変わるのは、記録が消える
操作として乱暴すぎる。除名（台帳が空の場合のみ）とは影響の大きさが違う。
