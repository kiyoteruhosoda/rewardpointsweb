# ADR-0010: ポイント台帳を追記型とし、訂正を打ち消しトランザクションで表現する

- ステータス: 承認
- 日付: 2026-08-01
- 関連: ADR-0009（家族グループを共有単位とする）
- 対象: `bounded_contexts/reward_points/`

## コンテキスト

ポイントの履歴は、付与する親と付与される子どもの双方が参照する。
このとき次の性質が求められる。

1. **訂正の追跡可能性** — 誤入力の修正で履歴を UPDATE / DELETE すると、子どもの側からは
   記録が黙って書き換わったように見える。動機づけを目的とするシステムにおいて、
   台帳への信頼が失われることの影響は大きい。
2. **操作者の記録** — 家族内の複数の親が同一の台帳を操作するため、
   誰がいつどの操作を行ったかを常に特定できる必要がある。
3. **二重登録の防止** — モバイルからの操作で送信ボタンの二重タップが起こりうる。

また、要件確認の結果として次が確定している。

- マイナス残高を許容する（前借りの運用を認める）
- ポイントの有効期限および期間リセットは設けない

## 決定

`point_transaction` を追記専用（append-only）テーブルとし、UPDATE および DELETE を行わない。

```
point_transaction
  id
  ledger_id
  amount                    -- 符号付き整数 / CHECK (amount <> 0)
  reason                    -- 付与・消費の理由（自由入力）
  granted_by_membership_id  -- 操作を行った membership
  occurred_at               -- 出来事の発生日時（UTC、遡って入力可）
  created_at                -- レコード作成日時（UTC）
  reversal_of_id NULL       -- 打ち消し対象の transaction / UNIQUE
  idempotency_key           -- UNIQUE (ledger_id, idempotency_key)

  INDEX (ledger_id, occurred_at DESC, id DESC)
```

### 残高

残高は保持せず、`SUM(amount)` により導出する。
有効期限・期間リセットがないため、集計対象は常に台帳の全レコードとなり、
スナップショットや失効ジョブは不要である。

家庭内での利用を前提とすると 1 台帳あたりのレコード数は年間で数百件規模に収まると見込まれ、
全件集計の負荷は問題にならない。将来、性能上の必要が生じた場合に限りスナップショットを導入する。

### 訂正

訂正は元レコードの逆符号のレコードを追加することで表現する。

- `amount` は元レコードの符号を反転した値
- `reason` は元レコードの内容を引き継ぐ
- `reversal_of_id` に元レコードの ID を設定する
- `reversal_of_id` は UNIQUE とし、同一レコードの二重取り消しを DB 制約で防ぐ
- 打ち消しレコード自体を打ち消すことは許可しない（`reversal_of_id` が設定されたレコードを
  対象とする打ち消しはアプリケーション層で拒否する）

UI 上は、打ち消し済みのレコードと打ち消しレコードを対で表示し、取り消された事実を明示する。

### 残高チェック

マイナス残高を許容するため、消費時の残高検証はドメイン層で行わない。
負の残高は表示上の扱い（負値の明示、0 までの必要ポイントの提示）のみで対応する。

### 冪等性

加算・消費の API はクライアント生成の `idempotency_key` を必須とする。
`UNIQUE (ledger_id, idempotency_key)` に抵触した場合は、エラーとせず既存レコードを返す。

## 結果

### 良い点

- 履歴が改変されないため、台帳の内容について家族内で疑義が生じにくい。
- 残高を保持しないことで、加算と残高更新の不整合が原理的に発生しない。
- 追記のみのモデルは、ネイティブ版（Flutter + SQLite）とのオフライン同期において
  レコードの追加のみを転送すればよく、更新の競合解決が不要になる。

### トレードオフ

- 履歴の表示件数が訂正の分だけ増える。UI 側で対の表示を実装する必要がある。
- 誤って入力した `reason` の文言そのものは残り続ける。
  個人情報等の削除要求には別途対応を要する（現時点では家庭内利用のため許容する）。
- 残高の都度集計はレコード数の増加に対して線形に劣化する。上記の見込みを超えた場合に再検討する。

## 検討した代替案

### 台帳に残高カラムを持ち、トランザクションと同時に更新する

残高取得は速いが、加算処理と残高更新の整合性を常に保証する必要があり、
オフライン同期を行う際に競合解決の対象が増える。現時点の規模では利点が小さい。

### 論理削除（`deleted_at`）による訂正

実装は単純だが、既定の一覧から削除済みレコードが消えるため、
「記録が黙って書き換わったように見える」という本来の課題を解決しない。

### レコードの UPDATE による訂正

操作履歴が残らず、複数の親が操作する前提と両立しない。
