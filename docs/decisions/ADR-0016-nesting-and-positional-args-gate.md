# ADR-0016: ネスト深度と位置引数の数を preview ルールの別コマンドで機械検証する

- 日付: 2026-08-01
- 状態: 承認（ADR-0008 の「preview のルールは使わない」を一部置き換え）

## 文脈

ADR-0008 は複雑度（`C901`）・分岐（`PLR0912`）・文の数（`PLR0915`）・引数の数
（`PLR0913`）を必須ゲートに入れたが、開発標準の**ネスト深度 3 段**と
**位置引数 3 個**は見送った。該当ルール（`PLR1702` / `PLR0917`）が Ruff の
preview 扱いで、「マージを止めるゲートを preview の上に置かない」と判断したため。
安定版入りを待っていたが、Ruff 0.15 系でも両ルールは preview のままで、
その間この 2 基準はレビュー頼みが続く。計測時点の違反は `PLR1702` が 1 件、
`PLR0917`（3 個）が 38 件だった。

## 決定

`PLR1702`（ネスト 3 段）と `PLR0917`（位置引数 3 個）を、`ruff check` 本体とは
**別の明示 select コマンド**として必須ゲートに加える。

```
uv run ruff check --preview --select PLR1702,PLR0917 .
```

閾値は `[tool.ruff.lint.pylint]` の `max-nested-blocks = 3` /
`max-positional-args = 3`。違反 39 件は基準値のまま全件修正して導入した
（緩い値からの段階導入は採らない。ADR-0008 と同じ方針）。

## 理由

- **preview の影響をこの 2 ルールに閉じ込められる**。CLI の `--select` は設定の
  `select` を置き換えるため、このコマンドで動くのは指定した 2 ルールだけ。
  `preview = true` を設定に書く方式と違い、安定版ルールの preview 挙動
  （既存ゲートの判定が変わるリスク）を持ち込まない。
- **挙動が変わったときの被害が読める**。preview 由来で判定が変われば落ちるのは
  この専用ステップだけで、原因の切り分けに迷わない。閾値と対象ルールは
  pyproject / Makefile / CI に明示してある。
- **違反の大半は宣言だけで直せた**。`PLR0917` の 38 件はキーワード専用引数
  （`*` の挿入）でほぼ解消できる。FastAPI のハンドラ・`Depends()` 用の組み立て
  関数・pytest のテスト関数はいずれもフレームワークがキーワードで呼ぶため、
  呼び出し側の書き換えはユースケースの組み立てとテストヘルパーの数か所で済んだ。
  `PLR1702` の 1 件は import 解決の分岐をヘルパー関数へ抽出した。

検討して捨てた代替案:

- **安定版入りを待ち続ける**: いつ入るかの見込みが立たず、その間 2 基準が
  レビュー頼みのまま残る。preview の露出を 2 ルールに限定できる以上、
  待つ利益が小さい。
- **`preview = true` + `explicit-preview-rules = true` を設定に書く**: 有効になる
  ルールは絞れるが、安定版ルールの preview 挙動（判定の変化）が本体の
  `ruff check` にも及ぶ。ADR-0008 が避けたかったのはまさにこれ。
- **AST を読む自作テストで検証する**（`test_layer_dependencies.py` 方式）:
  依存は増えないが、Ruff が既に持っている検査を二重に実装・保守することになる。

## 影響

- `make check` / CI の Backend ゲートに 1 コマンド増える（Ruff Check の直後）。
- 新規コードはネスト 4 段以上・位置引数 4 個以上で落ちる。超える場合は関数を
  割るか、引数を `*` でキーワード専用にする（FastAPI ハンドラ・DI の組み立て・
  テストはキーワード呼び出しなので `*` を足すだけでよい）。
- 両ルールが安定版へ入った時点で、本体の `select` へ移して専用コマンドを畳む。
- ユースケースの `__init__` をキーワード専用へ変えたため、組み立ては
  `presentation/dependencies.py` のようにキーワードで書く。
