# ADR-0041: 割り当てられた人は、初めての SSO ログインで口座を作って迎える

- 日付: 2026-09-16
- 状態: 承認（ADR-0029 の決定 1「SSO で利用者を作らない」を置き換える）

## 文脈

ADR-0029 は「SSO で利用者を作らない」と決めた。当時の理由は 2 つある。

- **誰がこのアプリを使えるかを、管理画面と招待の 2 つだけで決めたい。** IdP 側で誰かを
  作った瞬間に、こちらにも利用者が生えるのを避けたかった。
- **作った口座が家族のどこにも属さず、宙に浮く。**

そのうえで ADR-0033 が「メールアドレスで寄せる」を既定で閉じた。この 2 つが重なって、
⚠ **まだ結び付いていない新しい人は、SSO では一切入れなくなった。** 結び付きは
`(issuer, sub)` の行が先に要るが、その行を作る道が「メールで寄せる（閉じている）」か
「ローカル口座に入ってから連携する（ADR-0036。ローカル口座が要る）」しか無い。
**新しい人には、最初の 1 回の入り口が無い**（鶏と卵）。

状況が 2 つ変わった。

1. **assay に「アプリの割り当て」が入った**（idp の ADR-0054）。判定は code を発行する
   唯一の経路の先頭にあり、⚠ **割り当てが無い人には code を出さず、assay の画面で 403 を
   返す**（RP へは戻さない）。本番は 2026-09-16 に `enforce` へ切り替わった。
2. **ユーザーが、新しい人の最初の結び付けを「assay の割り当てで通す」と決めた**（task #61
   の決定 A）。RP は、割り当てられた人が初めて SSO で来たときに口座を作る。

ADR-0029 の 1 つ目の理由は、割り当てで解ける。「誰が使えるか」を決める場所が、
IdP で**人を作ったとき**から、IdP で**このアプリを割り当てたとき**へ移る。割り当ては
アプリごとの明示の操作なので、「IdP に人が居るだけで生える」にはならない。

2 つ目の理由は、ADR-0018 で既に解けている。**家族に属さない親（`member`）は、このアプリの
正規の初期状態である** ——家族を作れば owner、招待を受ければ parent になる。管理画面で
作る口座も、この形で生まれている。

## 決定

### 1. 初めての相手は、寄せられなければ作る

`ResolveFederatedAccount` の順番を次のようにする。

1. `(issuer, sub)` の結び付きがあれば、その利用者（従来どおり）
2. 同じメールアドレスの口座があり、寄せてよければ寄せる（ADR-0033。既定は寄せない）
3. どちらでもなければ**口座を作り**、結び付ける

⚠ **「code を持って戻ってきた＝このアプリを使ってよい人」をそのまま契約にする。**
割り当てを RP が受け取る口（クレーム・問い合わせ）は作らない（task #63 の決定：RP に判定の
モードを知らせると、同じ分岐が RP の数だけできる）。assay の ID トークン・userinfo には、
割り当てに関するクレームは載らない。

### 2. 作る口座は、管理画面で作るときの既定と同じ形にする

| 項目 | 値 |
|---|---|
| ロール | `member`（親。ADR-0018） |
| 家族 | 属さない（自分で作るか、招待を受ける） |
| `password_hash` | `NULL`（ローカルのパスワードは無い。ADR-0034） |
| `email` / `display_name` | IdP の値（以後もログインのたびに書き直す。ADR-0038） |
| `username` | IdP の `preferred_username`（下の 3） |

### 3. `username` は `preferred_username` から作り、使えなければ断る

このアプリのログイン識別子は `username`（NOT NULL・UNIQUE。ADR-0011）で、SSO の
突き合わせに使う `email`（任意）とは別の列である。作るには値が要る。

- `preferred_username` を識別子の規則（`shared/domain/auth/username.py`）で正規化する
- ⚠ **無い・規則に合わない・既に使われている、のどれでも作らずに断る**
  （`sso_username_unavailable`）。ログには理由の区別（`missing` / `invalid` / `taken` /
  `raced`）だけを残し、値は残さない（PII）
- ⚠ **黙って連番（`parent2`）や別の値を付けない**

### 4. 同じメールアドレスの口座が既にあるなら、作らずに断る（⚠ 意図して残す）

寄せる設定が閉じているとき（既定）、IdP のメールアドレスと同じ `email` を持つ口座が
既にあれば、**作らずに `sso_account_not_linked` で断る。**

⚠ **これは直し忘れた歪みではなく、意図して残す形である。** blobshare にも「メールが
一致する新規は断る」があり、task #98 はそれを「整理する」対象に挙げている。このアプリで
残す理由は 3 つある。

- **作ると、同じ人の口座が 2 つになる。** 既存の口座には家族・台帳・パスキーが付いている。
  2 つ目は空の親で、本人はどちらで入ったのか分からなくなる。
- **`users.email` は UNIQUE である。** 2 つ目を作るならメールアドレスを外すしかなく、
  そのうえで次のログインの写しの更新（ADR-0038）も、ぶつかるので書けない。
  **メールアドレスを持てない親**という、どこにも想定の無い口座ができる。
- **メールで寄せる設定は既定で閉じている**（ADR-0033）。assay の `email_verified` は
  「テナント管理者がそう主張している」であって、本人の証明ではない。だから黙って寄せも
  しない。**寄せも作りもできないので、断るしかない。**

本人がやることは、**その口座へパスワード（またはパスキー）で入り、設定画面から連携する**
（ADR-0036）ことである。画面の文言もそう案内する。

### 5. 設定で切り替えられるようにはしない

「作る／作らない」をフラグにしない。ADR-0029 が捨てた理由（使わない枝が残り、いつか
切り替えられたときの振る舞いを誰も確かめていない）は今も同じである。**作らない側の枝は
消す。**

## 理由

**入り口が無いことは、安全ではなく故障である。** 新しい人が SSO で入れない状態は、
結局「管理者が口座を手で作り、メールアドレスを設定し、寄せる設定を開ける」運用へ
押し出す。ADR-0033 が閉じたものを、運用で開け直すことになる。

**誰を通すかを決める場所は 1 つにする。** 割り当てを RP 側でも確かめる（assay に聞き直す・
クレームを読む）と、同じ判断が 2 か所に分かれ、食い違ったときにどちらが正か決められない。
assay が code を出した時点で、判断は終わっている。

**作れないときに別の形で作らないのは、どちらも取り返しがつかないから。** 連番の
`username` は本人がパスワードを持たないので気付く機会が無く、メールアドレスを外した
2 つ目の口座は、写しの更新でも直らない。断れば、少なくとも**画面に理由が出る。**

### 検討して捨てた案

- **RP が割り当てを受け取る口を作る**（ID トークンにクレームを載せる・assay の管理 API に
  聞く）。task #63 で捨てた「RP にモードを知らせる」と同じ形になる。判定が 2 か所に
  分かれるうえ、assay が断った相手はそもそも戻ってこない。
- **作るかどうかを設定にする**（`OIDC_AUTO_PROVISION` など）。決定 5。
- **`username` が衝突したら連番を付ける**。決定 3。ユーザーの決定（2026-09-16）でもある。
- **`username` を `sub` や乱数にする**。衝突はしないが、本人も管理者も読めない識別子になり、
  あとからパスワードを持たせたときに入力できない。
- **同じメールアドレスの口座があるとき、メールアドレス無しで作る**。決定 4。
- **同じメールアドレスの口座があるとき、寄せる設定を無視して寄せる**。ADR-0033 が閉じた
  理由（`email_verified` は本人の証明ではない）がそのまま戻る。

## 影響

- ⚠ **この決定は、`OIDC_ISSUER` の IdP が割り当てで人を絞っていることに乗っている。**
  assay が `record_only` に戻る、アプリの `assignment_mode` が `EVERYONE` になる、
  あるいは割り当ての無い別の IdP をつなぐと、**そのテナントの全員がこのアプリに口座を
  持てる。** 戻すときはこの影響を込みで判断する。IdP 側で絞れないときの二重の歯止めは、
  従来どおり `OIDC_ALLOWED_EMAIL_DOMAINS` だけである
- ⚠ **`preferred_username` が要る。** assay は `profile` scope を求めたときだけ載せる。
  既定の `OIDC_SCOPES` は `openid profile email` なので満たしているが、scope を削ると
  **新しい人だけが `sso_username_unavailable` で入れなくなる**（既に結び付いている人は
  影響を受けない）
- **子ども（メールアドレスも IdP の口座も持たない利用者）は変わらない。** 招待の受諾で
  生まれ、パスワードかパスキーで入る（ADR-0011・ADR-0035）
- **作られた親はパスワードを持たない。** 入り口は IdP だけで、ADR-0036 の解除は
  `sso_last_entrance` で止まる。パスワードを持たせるのは管理者の明示の操作だけ
- **エラーコードが 1 つ増えた**（`sso_username_unavailable`）。`sso_account_not_linked` の
  意味は「同じメールアドレスの口座が既にあり、まだ結び付いていない」に絞られた
- **ログに `sso_account_provisioned` が増えた**（口座を作った往復）。結び付けだけの往復は
  従来どおり `sso_identity_linked`
- **表・移行は増えない。** 既存の `users` / `user_roles` / `federated_identities` に書く
- ADR-0040 の定期照合で `unknown`（IdP から消えた）になった人は、結び付きが外れて口座は残る。
  同じ人が IdP で作り直されて来ると、**メールアドレスが同じなら決定 4 で断られる**
  （口座は 2 つにならない）。管理者が古い口座を消すか、本人が入れるなら連携し直す
