# ADR-0020: 子ども宛の招待は親メンバーも配れる（親を招くのは owner のまま）

- 日付: 2026-08-02
- 状態: 承認
- 関連: ADR-0009（家族の認可表 — 「招待は owner のみ」を部分的に置き換える）、
  ADR-0011（子アカウントの認証）、ADR-0013（所属は 1 家族まで）
- 対象: `bounded_contexts/reward_points/`、`frontend/src/`

## 文脈

ADR-0009 は招待コードの発行を owner だけに許していた。理由は「誰をこの家族へ
入れるかは owner が決める。招待は家族の構成を変える操作で、除名と対になる」。

しかし子の追加（`can_create_child`）は親（owner / parent）に許してある。その結果、
招待で加わった親が次の順路で詰まる。

1. 子どもの参加を作る（できる）
2. 台帳にポイントを記録する（できる）
3. **その子にログインを渡す招待コードを発行する（できない — 403）**

自分で追加した子どもに、自分でログインを渡せない。owner が席を外していると、
子どもは自分の残高を見られないままになる。

## 決定

招待コードを配れる立場を、招く相手で分ける。

- **親（parent）の招待 … owner のみ。** 従来どおり。新しい大人を家族へ入れる操作。
- **子ども宛の招待 … 親メンバー（owner / parent）。** 指す先は同じ家族の未紐付けの
  参加者だけ（`target_membership_id` 必須 — ADR-0011）。

一覧と取り消しも同じ線で分ける。一覧は親メンバーに開き（配った本人が確かめられ
ないと渡し間違いを直せない）、取り消しはその招待の相手で判定する。

判定は `family_access_policy.can_invite(membership, invited)` の 1 か所。

## 理由

子ども宛の招待は**家族の顔ぶれを変えない**。参加者はすでに名簿にいて、台帳も
持っている。コードで変わるのは「その子が本人としてログインできるか」だけで、
ADR-0009 が owner に残したかった判断（誰をこの家族へ入れるか）には触れない。
参加を作れるのが親である以上、その続きも親でできないと経路が途切れる。

親の招待は逆で、家族に新しい大人が増える。owner を除名できる立場が増えることに
なるので、owner の判断に残す。

### 代替案: 招待をすべて親に許す

シナリオは通るが、招待で加わった親がさらに別の親を招けるようになり、家族の
顔ぶれを owner が把握できなくなる。ADR-0009 の意図をそのまま失う。

### 代替案: owner だけが配れるまま、画面で説明する

「追加はできるがコードは owner に頼む」という運用は、二人で回している家庭では
毎回止まる。制約に見合う保護が無い（子ども宛のコードは新しい人を入れない）。

## 影響

- `IssueInvitationUseCase` / `RevokeInvitationUseCase` は `require_owner` をやめ、
  `membership_in` ＋ `can_invite` で判定する。owner 以外が親の招待を試みた場合は
  従来どおり 403（`family_access_denied`）。
- 招待の一覧（`GET /api/families/{id}/invitations`）が親メンバーにも 200 を返す。
  平文のコードは載らない（保存はハッシュのみ）ので、見えるのは「誰宛に、いつまで」。
- 画面の招待パネルは親メンバーに出す。「もう 1 人の親を招待」のボタンだけ owner に
  限る。
- ADR-0009 の認可表のうち「招待 = owner のみ」の行は、この ADR が置き換える。
