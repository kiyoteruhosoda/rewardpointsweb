# ADR-0038: 写しは IdP を正とし、メールアドレスを鍵扱いしない

- 日付: 2026-09-15
- 状態: 承認

## 文脈

idp の ADR-0049（属性の持ち主と連携の鍵）が、RP 側に 11 のギャップを挙げた。
このアプリに当たるのは 2 つで、**どちらも「メールアドレスを鍵として扱っていた」
時代の名残**である。

- **G4（I5）** —— 利用者の写しが**初回以降まったく更新されない**。名簿の口は
  `find_by_id` / `find_by_email` の 2 つだけで、写しを書き直す口が存在しない。
  IdP で改名・メール変更をしても、こちらの表示は永久に古いままになる。
- **G5（I1 の副作用）** —— `ClaimsMapping.apply` が `email` の空を
  `SsoEmailMissingError` で落としていた。⚠ **鍵ではないのに必須にしていた。**
  結び付きの鍵は ADR-0029 の時点で `(issuer, subject)` に決まっており、
  既に結び付いている相手はメールアドレスが無くても誰なのか分かる。

## 決定

1. **ログインのたびに写しを上書きする。** 名簿へ `refresh_profile` を足し、
   `(issuer, subject)` で引けた利用者の `email` と `display_name` を IdP の値で
   書き直す。
2. **メールアドレスを任意にする。** `FederatedUser.email` を `str | None` にし、
   `SsoEmailMissingError` を廃止する。断るのは**初回に既存の利用者を探すとき**
   だけで、そのときの理由は `sso_account_not_linked` に揃える。

## 理由

**写しは写しである。** 正は IdP にあり、こちらが持っているのは表示のための複製
でしかない。複製が更新されないのは、複製である以上ほぼ必ず間違いになる。

**断る場所を、必要な場所まで下げた。** 「メールアドレスが無い」は、それ自体では
失敗ではない。困るのは寄せる先を探せないときだけなので、判断を
`ResolveFederatedAccount._link_existing` へ移した。理由を
`sso_account_not_linked` に揃えたのは、**本人にできることがどちらも
「管理者に頼む」で同じ**だからである（区別を見せる相手が居ない）。

`SsoEmailMissingError` は残さず消した。誰も投げない例外と、対応する画面文言が
残っていると、**次に読む人が「まだ必須である」と読む。**

## 影響

- ⚠ **`/admin/users` で直した名前とメールアドレスは、次の SSO ログインで IdP の
  値へ戻る。** 直したい値は IdP 側で直す。
- ⚠ **ログインの識別子（`username`）は上書きしない。** IdP の名乗りは
  `display_name` に対応する（ADR-0011）。`username` を書き換えると、パスワードで
  入っていた人の入り口が消える。
- ⚠ **ぶつかる値は書かない。** `users.email` は一意なので、他の利用者が既に持って
  いる値を書くと**写しの更新でログインが 500 で落ちる**。その項目だけ見送り、
  `federated_profile_conflict` を記録する（値そのものは PII なので残さない）。
  長すぎる名乗りは `display_name` の桁数で切る（MySQL は厳格モードで溢れた値を
  通さない）。
- ⚠ **`email` が `None` のときは消さない。** 「空にしてほしい」ではなく
  「今回は分からない」である。メールアドレスを持たない利用者（ADR-0011）を
  ここで壊さないためでもある。
- エラーコード `sso_email_missing` が無くなった（画面文言も削除）。
- ⚠ **`OIDC_ALLOWED_EMAIL_DOMAINS` を入れている場合だけ、メールアドレスの無い相手は
  結び付いていても断られる**（`sso_email_not_allowed`）。ドメインで絞る運用は
  「メールアドレスが必ず来る」を前提にしているので、そのまま残した。⚠ **既定は空**
  なので、絞っていない構成では起きない。
