# ADR-0022: 記録の訂正を、打ち消しと書き直しの 1 操作として扱う

- ステータス: 承認
- 日付: 2026-08-02
- 関連: ADR-0010（ポイント台帳を追記型とし、訂正を打ち消しトランザクションで表現する）
- 対象: `bounded_contexts/reward_points/`

## コンテキスト

ポイントの入力は手打ちで、間違いが起こる。

- 量の打ち間違い（`1000` と打つつもりが `100`、桁を 1 つ多い）
- 符号の取り違え（加算のつもりで消費を押した）
- 理由の書き間違い
- 日付の取り違え（遡って入力するときに別の日を選んだ）

台帳は追記専用で、用意されている直し方は打ち消し（undo）だけだった。正しい内容に
するには、利用者が **打ち消してから、もう一度入力し直す** 必要がある。ここには
3 つの問題がある。

1. **途中で終われる。** 打ち消しただけで入力し直すのを忘れると、記録そのものが
   消えたのと同じ状態になる。片方だけが通信に失敗した場合も同じ。
2. **打ち直しの手間が大きい。** 直したいのが量だけでも、理由をもう一度打つ。
   間違えた理由が入力候補（`reason-suggestions`）に残っているため、直したはずの
   文言をまた選んでしまう。
3. **発生日時が動く。** 遡って入力した記録を打ち消して入れ直すと、`occurred_at` は
   入れ直した日になる。量を直しただけで、出来事の日付まで変わる。

## 決定

**訂正（correction）を 1 つの操作として用意する。** 元のレコードは書き換えない
（ADR-0010 のまま）。1 回の要求で台帳へ 2 行を足す。

```
POST /api/families/{family_id}/ledgers/{ledger_id}/transactions/{transaction_id}/corrections
{ "amount": 100, "reason": "おてつだい", "idempotency_key": "...", "occurred_at": null }
```

| 足す行 | 意味 | 参照 |
|---|---|---|
| 打ち消し | 元の行を無かったことにする | `reversal_of_id` = 元の行 |
| 訂正後 | 正しい内容 | `corrects_id` = 元の行 |

両方を 1 つの DB トランザクションで書く。どちらかが落ちればどちらも残らないので、
「打ち消しただけ」の状態は利用者からは作れない。

### `corrects_id`

`point_transactions` に自己参照の列を足す（NULL 可・UNIQUE）。

- 「この行は、どの行の言い直しか」を台帳自身が持つ。無いと、履歴に並ぶ 3 行目が
  無関係な新しい記録と区別できない。
- `ON DELETE SET NULL` にする。独立の成立で台帳ごと消すとき（ADR-0014）に、
  元の行と訂正後の行のどちらを先に消しても外部キーで拒まれないようにするため。
- UNIQUE は「1 つの記録を言い直せるのは 1 度だけ」を表す。訂正は必ず打ち消しを
  伴うため `reversal_of_id` の UNIQUE でも止まるが、対応が 1 対 1 であることを
  この表自身に持たせる。

### 発生日時

`occurred_at` を指定しなければ、**元の行の発生日時を引き継ぐ**。量や理由の
打ち間違いを直しただけで、出来事が今日へ動いてしまわないようにする。日付そのものを
間違えていた場合は `occurred_at` を指定して直す。

### 冪等性

1 回の訂正が 2 行を書くため、`UNIQUE (ledger_id, idempotency_key)` に収まるよう、
クライアントの鍵から段階ごとの鍵を導く（`IdempotencyKey.for_step`）。受け取る鍵の
上限は、分けた後も列に収まる長さ（`MAX_BASE_LENGTH`）までとする。

台帳の鍵の空間は 1 つしかないため、**分けた鍵と受け取る鍵の形を交わらせない**。

- 区切り文字（`#`）は分割の予約とし、クライアントの鍵には現れてはならない
  （記録・打ち消し・訂正のすべての API で弾く）。受け取ってしまうと、
  `<鍵>#reversal` をそのまま記録に使われたときに訂正の打ち消し行と衝突し、
  `append` が無関係な既存の行を返す。打ち消しを書いたつもりで書けておらず、
  元の記録と訂正後の記録の両方が残高に効く。
- それでも同じ鍵を**別の記録の訂正**へ使い回すことはできてしまうため、打ち消しの
  行を書いた直後に、その行が本当に自分の対象を指しているかを確かめる。違えば
  409（`idempotency_key_reused`）で断り、訂正後の行は書かない。

送り直しは打ち消しの UNIQUE に当たり、409（`transaction_already_reversed`）で
断る。打ち消しの操作と同じ扱いで、**二重に効いてしまうより、効かずに知らせる**。

### 訂正できないもの

| 対象 | 結果 |
|---|---|
| 打ち消しの行 | 409 `correction_of_reversal_not_allowed` |
| すでに打ち消された行 | 409 `transaction_already_reversed` |
| 訂正後の行 | 訂正できる（直した内容をさらに直せる） |

すでに打ち消された行を訂正できないのは、その行の内容はもう台帳に効いていない
ため。正しい内容は新しい記録として足す。

### 入力候補

訂正で言い直された行の理由は `reason-suggestions` に出さない。書き間違えた文言が
候補に残り続けると、直したはずの間違いを選び直してしまう。打ち消しただけの行は
これまでどおり数える（打ち消しは「その出来事が無かった」であって、文言が
誤りだったとは限らない）。

## 結果

### 良い点

- 「打ち消しただけ」で終わる状態が作れない。
- 直したいところだけを直せる。量を直すために理由を打ち直さない。
- 遡って入力した記録を直しても、出来事の日付は動かない。
- 追記専用のまま（ADR-0010）。履歴は誰の目にも残り、何をいつ直したかが追える。

### トレードオフ

- 1 回の訂正で履歴が 3 行になる（元・打ち消し・訂正後）。UI は印を付けて並べる。
- 間違えた `reason` の文言そのものは履歴に残る（ADR-0010 と同じ制約）。
- 訂正の 2 行は `granted_by` に訂正した人が入る。元の記録を誰が付けたかは
  元の行に残るが、履歴を追わないと分からない。

## 検討した代替案

### 打ち消しと記録を画面側で 2 回呼ぶ

サーバーの変更は要らないが、片方だけ通った状態が利用者に見える。オフラインに
なりやすい端末（PWA・モバイル）で起こりやすく、起きたときの見え方が
「記録が消えた」なので最も避けたい。

### 元のレコードを UPDATE する

最も簡単だが ADR-0010 で退けた選択そのもの。子どもの側から見て記録が黙って
書き換わり、台帳への信頼が失われる。

### `corrects_id` を持たず、打ち消しの後に普通の記録を足すだけ

列は増えないが、履歴の 3 行目が無関係な新しい記録と見分けられない。
「訂正した」という事実が台帳のどこにも残らず、追跡可能性という ADR-0010 の
目的を半分しか満たさない。
