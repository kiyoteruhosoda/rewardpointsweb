# ADR-0007: 人ごとのポイントを scope とメンバー単位アクセスの二段で守る

- 日付: 2026-07-30
- 状態: 承認

## 文脈

ネイティブアプリ（Flutter + SQLite の RewardPoints）を PWA へ移行する。移行に
あたって次の要件が加わった。

- ログインが必要になる（端末内 DB から共有サーバーへ移る）。
- ポイントは**人ごと**に持つ。
- ある人が管理するメンバーを、**他のログインアカウントへ共有できる**。
- **メンバー本人は自分のポイントを見られるが、変更はできない**。履歴も見られる。

本テンプレートの認可は scope（権限コード値）で行う（ADR-0002）。しかし scope
だけでは今回の要件を満たせない。`point:manage` を持つ管理者が「自分のメンバー」
だけを触れる、という判断は scope の集合では表せない（誰のメンバーかという関係が
scope に現れない）。

ネイティブ版では端末の所有者＝唯一の利用者だったため、この問題は存在しなかった。

## 決定

認可を**二段**に分ける。

1. **scope** — その操作を行える立場かどうか。エンドポイントに宣言する。
   `member:view` / `member:manage` / `point:view` / `point:manage` の 4 つ。
2. **メンバー単位アクセス** — *その* メンバーを触れるかどうか。到達経路から
   `VIEW` / `MANAGE` を導く。Domain の `MemberAccessPolicy` が唯一の判定者。

到達経路は 3 つで、複数該当するときは強い方を採る。

| 経路 | 範囲 |
|---|---|
| 所有者（`members.owner_user_id`。登録した人） | `MANAGE` |
| 共有された人（`member_shares.access_level`） | 共有時に決めた範囲 |
| 本人（`members.linked_user_id`） | `VIEW` のみ |

ロールへの付与は `manager` = 4 つすべて、`member` = `member:view` + `point:view`。

共有相手の指定は**メールアドレス**で行う。共有の管理（一覧・追加・解除）は
**所有者のみ**で、`MANAGE` で共有された相手は記録はできても配り直しはできない。
残高は `point_entries` の合計として毎回導出し、残高列は持たない。

## 理由

- **scope だけでは足りず、関係だけでも足りない**。scope が無ければ「そもそも
  ポイントを操作する立場ではない」ことを表せず、メンバー本人にまで変更 API の
  入り口が開く。関係が無ければ「他人のメンバーを触れない」ことを表せない。
  両方を通らないと操作できない形にした。
- **本人は `VIEW` 止まり**。要件そのもの。scope（`member` ロールに
  `point:manage` を与えない）と、関係（`linked_user_id` は `VIEW` しか生まない）の
  両方で止める。どちらか一方の設定を間違えても変更はできない。
- **複数経路では強い方を採る**。自分自身をメンバーとして登録した管理者は、
  所有者としての `MANAGE` を保つ。本人でもあるという理由で所有者の権限を弱める
  のは筋が通らない。要件が禁じているのは「メンバーという立場での変更」であって、
  「管理者が自分のポイントを記録すること」ではない。
- **到達できない相手には 404（`member_not_found`）を返す**。403 だと「その ID の
  メンバーは存在する」ことが分かる。到達はできるが変更権が無い場合だけ
  403（`member_access_denied`）にする。
- **共有はメールアドレスで指定する**。ユーザー一覧を返す API を作ると、
  `user:manage` を持たない管理者にも全アカウントが見えてしまう。共有先の一覧に
  出すのは、自分が共有した相手だけ。
- **1 アカウントを紐付けられるメンバーは 1 人だけ**（`linked_user_id` を一意に
  する）。「自分のポイント」が一意に決まらないと、本人向けの画面が成立しない。
- **残高を持たない**。履歴が唯一の事実で、残高は導出値。残高列を置くと、履歴を
  1 件消したときに整合を取る処理が必要になり、そこがずれると誰も気付けない。
  一覧では 1 クエリでまとめて読み、メンバーごとに合計する（N+1 にしない）。
- **消費で残高不足を拒まない**。「先に景品を渡してから記録する」順序が実際に
  起こる。残高は導出値なので負の値もそのまま表せる。

## 影響

- マイグレーション `0004_reward_points`（`members` / `member_shares` /
  `point_entries`）と `0005_seed_reward_points_permissions`（権限 4 件の投入）を追加。
- 権限コードが 4 つ増える。正本は `shared/domain/auth/master_data.py`。
- 応答に `access_level` を含める。画面は変更 UI の出し分けにこれを使い、
  ロール名では判断しない。
- **共有の管理（一覧・追加・解除）は所有者だけ**。`MANAGE` で共有された相手は
  ポイントを記録できるが、共有を配り直せない。許すと、所有者の知らないところで
  共有先が増え、所有者が配った他の共有を取り消すこともできてしまう。誰に渡すかを
  決めるのは、そのメンバーを登録した人だけにする。
- **メンバーの削除も所有者だけ**。`MANAGE` で共有された相手に許すと、所有者の
  メンバーと履歴すべてを消せてしまう。記録する権限と、消してしまう権限は分ける。
- 応答に `is_owner` を含める。画面は削除ボタンと共有パネルの出し分けにこれを使う
  （`access_level` では所有者と `manage` 共有先を区別できない）。
- **アカウント削除との関係**を参照ごとに決めた。本番（MariaDB）は外部キーを検査
  するため、決めておかないと参照が残ったアカウントの削除が 500 になる。

  | 参照 | アカウント削除時 | 理由 |
  |---|---|---|
  | `members.owner_user_id` | **削除を拒む**（409 `user_still_owns_members`） | 所有者が消えたメンバーは誰も管理できない。黙って消すとポイント履歴まで失われる |
  | `members.linked_user_id` | `SET NULL` | メンバーは残る。本人ログインの紐付けだけが外れる |
  | `member_shares.user_id` | `CASCADE` | 共有先が消えれば、その共有はもう意味を持たない |
  | `point_entries.recorded_by_user_id` | `SET NULL` | 履歴はメンバーのもの。記録者が消えても履歴は残す |

  無効化したいだけなら `is_active` を偽にする（削除は不要）。
- メンバー本人のメールアドレスは一覧に出さない（`has_linked_user` の真偽のみ）。
  共有先にまで本人のアドレスを見せる理由が無い。
- ネイティブ版にあった JSON エクスポート／インポートは移していない。共有サーバー
  上のデータになったため、端末間の持ち運び手段としての役目が無くなった。
