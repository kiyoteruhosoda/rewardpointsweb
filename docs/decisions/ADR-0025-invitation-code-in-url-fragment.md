# ADR-0025: 招待コードは URL の断片で運ぶ

- 日付: 2026-08-09
- 状態: 承認

## 文脈

招待の発行で渡していたのはコードだけで、受け取った人は「どの画面を開き、どこへ
打ち込むか」を別に教わる必要があった。コードは 1 度きりの表示で、打ち間違えても
確かめようがない。開くだけで入力済みの状態から始められる URL を渡したい。

一方で招待コードは、有効な間そのまま家族へ入れる capability そのものである。DB に
はハッシュしか置いていない（ADR-0009）が、URL のどこに載せるかで経路上の扱いが
変わる。

- クエリ（`?code=...`）はリクエストラインの一部としてサーバーへ送られる。
  Docker 構成のリバースプロキシ（`docker/nginx/default.conf`）は既定のアクセスログを
  そのまま使うため、平文のコードがログに残る。アプリのリクエストログも同じ経路に
  ある。ログを読める人は、有効期限の間そのコードで家族へ入れる。
- 断片（`#code=...`）はブラウザがサーバーへ送らない。アクセスログにも `Referer`
  にも現れず、読み取れるのは URL を開いた本人のブラウザだけ。

## 決定

招待コードは **URL の断片（`#code=...`）** で運ぶ。クエリ文字列には置かない。
組み立てと読み取りは `frontend/src/services/invitationLink.ts` に集約し、受け取り側の
3 画面（`/join`・`/login`・`/families`）はすべてそこを通す。

## 理由

- **出所で止まる。** プロキシの設定でクエリを伏せる方法もあるが、守られるのは
  その設定を持つ 1 台だけで、前段に別のプロキシが増えれば同じ問題が戻る。断片は
  ブラウザが送らないので、経路上のどこにも現れない。
- **ログの情報量を落とさない。** クエリを一律に伏せると、他のリクエストの調査で
  見たい値まで消える。
- **既存の受け渡しに合わせられる。** コードは元から画面間で URL に載せて運んで
  いた（`/join` → ログイン → `/families`）。運び方だけを差し替えれば済み、
  サーバー側の変更は要らない。
- 捨てた案: **ワンタイムの引き換え URL をサーバーで発行する。** 経路上に平文が
  残らない点は同じだが、テーブルとエンドポイントが増える。いまの招待コードは
  すでにハッシュ保存・期限付き・取り消し可能で、足りていないのは運び方だけだった。

## 影響

- 3 画面はコードを `useLocation().hash` から読む（`useSearchParams` ではない）。
  1 か所でもクエリへ戻すと、そこから先が平文でログに載る。回帰は
  `frontend/src/services/invitationLink.test.ts` が `?` を含まないことで検査する。
- 断片はサーバーに届かないため、サーバー側でコードの有無を見た出し分けはできない。
  読み取りと表示は必ずブラウザ側で行う。
- 断片はブラウザの履歴に残る。共用端末で招待リンクを開いた場合は、履歴からコードを
  読める（コードは 1 度使うと無効になり、期限は `FAMILY_INVITATION_TTL_SECONDS`）。
- 招待リンクの出所は発行した画面の `window.location.origin` を使う。設定の
  `APP_BASE_URL`（メール本文の生成元）は既定が空で、空のまま使うと開けない URL に
  なるため参照しない。
