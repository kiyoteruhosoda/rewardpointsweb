# ADR-0039: 認証の強度は、要求したら確かめる

- 日付: 2026-09-15
- 状態: 承認

## 文脈

idp の ADR-0049 の **G8（I8）**。`acr_values` を送って戻りの `acr` を照合して
いるのは 7 本中 3 本だけで、**このアプリは送っても確かめてもいなかった**。
ADR-0043 で予約語（`urn:assay:ac:mfa` / `urn:assay:ac:single`）を用意した目的が、
ここでは効いていない。

`acr_values` は**送っただけでは何の保証にもならない。** IdP 側のポリシーの
綴り違い 1 つで条件が外れ、単要素のログインが黙って通る。RP がそれに気付ける
唯一の手段が、返ってきた `acr` を要求と突き合わせることである。

## 決定

`OIDC_ACR_VALUES`（空 = 要求しない。既定）を足し、

- 認可要求に `acr_values` を載せる（ログインの往復・連携の往復の両方）
- 戻ってきた ID トークンの `acr` が要求のいずれかと一致することを確かめる。
  ⚠ **一致しない場合も、`acr` が返ってこない場合も断る**（`sso_acr_not_satisfied`）

判断は `RequestedAuthenticationContext` が 1 つだけ持つ。

## 理由

**要求したら確かめる。さもなければ要求しない。** 送りっぱなしの `acr_values` は、
運用している人に「多要素を強制した」と読ませるだけで、実際には何も強制していない
——**設定として存在するのに一度も効かない**という、G7 と同じ形の嘘になる。

`acr` が無いときに通さないのが肝である。「返ってこなかった＝満たした」と読むと、
**要求を無視する IdP に対して何の防御にもならない。** 既定を空にしてあるので、
予約語を持たない IdP へつないでいるあいだは従来どおり動く（fail closed になるのは
明示的に要求したときだけ）。

⚠ **`amr` は使わない。** RFC 8176 の `amr` は使われた方式の一覧であって強度では
ない。外部 IdP 経由はその先で何が使われたかを IdP 自身も知らないため、値の並びから
多要素かどうかは読み取れない。

## 影響

- `OIDC_ACR_VALUES` を入れると **fail closed** になる。IdP 側のポリシーを先に
  用意してから入れること。綴りが 1 文字違うと**誰も入れなくなる**
  （パスワード・パスキーの入り口は残る）。
- 連携の往復（ADR-0036）にも同じ関門が掛かる。弱い認証で通った往復が、そのまま
  新しい入り口になるのを防ぐため。
- エラーコード `sso_acr_not_satisfied` が増えた（画面文言・`OPERATIONS.md` の表も）。
