### T2 「止めたら届く」の残り 2 つ

idp の ADR-0049 I7 は 3 つを挙げている——back-channel logout の受け口・**短命の
アクセストークン**・**定期照合**。1 つ目は ADR-0032 で入った。残りは 2 つ。

- **アクセストークンの寿命**が、受け口の落ちていたときの上限時間になる。
- **定期照合**。`federated_identities.last_login_at` を持っているので、IdP の利用者
  一覧と突き合わせて、消えている・止まっている相手を無効化できる。IdP 側に一覧を
  引く口（管理 API）が要る。

⚠ **いまの assay は「利用者を止めた」ときに通知を送らない**（送るのはログアウトの
ときだけ）。定期照合が無いと、管理者による停止はどの経路でも届かない。

### T3 ローカルのログインにも多要素を強制できるようにする

ADR-0035 で「ローカル口座を意図して持つ」と宣言した。宣言した以上、認証系が 2 つある
ことを前提にした運用がこちら側にも要る。棚卸し（入れる手段の一覧）は入ったので、
残りは**強制**である。

⚠ **IdP 側で `require_mfa` を掛けても、このアプリのローカルログインは素通しである。**

- ⚠ **子どもには掛けられない**（ADR-0011。認証アプリを持たない前提）。掛けるなら
  ロールごとか、利用者ごとになる。
- 強制したとき、まだ登録していない利用者をどう扱うか

### T4 本人の操作で IdP の口座と結び付ける導線

ADR-0033 で `OIDC_LINK_BY_EMAIL` の既定を倒した。⚠ **このアプリは SSO で利用者を
作らない**（ADR-0029）ので、倒したままだと **まだ結び付いていない人は SSO で入れない**
（パスワードでは入れる）。

本筋は idp の ADR-0049 I9 ——**本人がログイン済みの状態で、設定画面から連携する**。

- 設定画面に「SSO と連携する」を置き、押すと認可要求へ送り出す
- 戻ってきた `(issuer, sub)` を、**いまログインしている利用者**へ結び付ける
- ⚠ **既に別の利用者へ結び付いている `(issuer, sub)` は断る**（横取りになる）
